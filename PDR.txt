# 1. PROJECT OBJECTIVE

Build the official website for **Layton Patrick**, an independent film production company.

This is deliberately **not** a conventional production-company slate website.

The company is new and does not require a public slate at launch. The website must instead establish the company through:

* prestige;
* selectivity;
* filmmaker-led development;
* restraint;
* seriousness;
* international ambition;
* premium independent cinema.

The creative benchmark is the confidence and simplicity associated with premium independent film companies such as A24, while remaining an original Layton Patrick identity.

The existing Layton Patrick material establishes a highly restrained visual system: narrow black wordmark, monochromatic typography, large negative space, thin rules and editorial layouts. The company website should continue that language rather than introduce a conventional corporate identity.

# 5. CRITICAL MICROSOFT 365 RULE

`Layton@laytonpatrick.com` is already operational through Microsoft 365.

This email configuration is **production infrastructure and must not be disrupted**.

Codex must not:

* delete Microsoft MX records;
* replace Microsoft MX records;
* edit Microsoft Autodiscover records unnecessarily;
* replace the existing root SPF record;
* change Microsoft DKIM records;
* change existing DMARC records;
* move the mailbox to Resend;
* use Resend as an inbound mailbox;
* change GoDaddy nameservers merely to deploy the website.

Microsoft documents that the MX record determines where incoming mail is delivered and recommends the Microsoft 365 SPF record for Exchange Online. It also warns against creating multiple SPF records for the same domain.

**Microsoft 365 email must continue working before, during and after website deployment.**

---

# 6. DNS SAFETY PROCEDURE

Before making **any** DNS change at GoDaddy:

1. Open GoDaddy DNS management for `laytonpatrick.com`.
2. Capture screenshots of the complete DNS zone.
3. Export DNS records if GoDaddy provides an export function.
4. Record all existing:

   * MX;
   * TXT;
   * CNAME;
   * SRV;
   * DKIM;
   * DMARC records.
5. Confirm `Layton@laytonpatrick.com` can send and receive mail.
6. Only then add website-related DNS records.

Do not delete an existing record merely because a new provider displays another record.

# 52. RESEND — ISOLATED SUBDOMAIN

Resend must **not** authenticate the root domain for this project.

Authenticate:

```text
forms.laytonpatrick.com
```

Resend itself recommends using a subdomain to isolate transactional sending reputation and intent.

This deliberately separates:

```text
Microsoft 365:
laytonpatrick.com
```

from:

```text
Resend:
forms.laytonpatrick.com
```

---

# 53. WHY THE SUBDOMAIN IS REQUIRED

The production mailbox uses Microsoft 365.

Microsoft currently expects its mail authentication at the root domain.

Using:

```text
forms.laytonpatrick.com
```

for Resend means its SPF/DKIM configuration exists in a **separate DNS namespace** and does not require replacing the Microsoft 365 root SPF record.

This is materially safer than attempting to configure two unrelated mail systems at `@`.

Microsoft explicitly states that a domain should not have multiple SPF records.

---

# 54. RESEND DNS PROCEDURE

In Resend:

1. Create account.
2. Add domain:

```text
forms.laytonpatrick.com
```

3. Resend will display authentication records.
4. Copy those records exactly.
5. Open GoDaddy DNS.
6. Add only the records required for the Resend subdomain.
7. Return to Resend.
8. Verify SPF.
9. Verify DKIM.
